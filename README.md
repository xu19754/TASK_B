## 一、项目简介

本仓库是小组项目的主代码仓库，用于统一管理项目代码、记录开发进度和整合各成员的工作成果。

小组采用 **Git 分支协作开发模式**：每位成员根据自己的职责在独立的分支上进行开发，阶段性完成后通过 Pull Request（PR）将代码合并到 `main` 主分支，随后所有成员同步主分支的最新内容。

## 三、协作开发流程

### 第一步：在个人分支上开发

每位成员在自己的分支上编写、修改，调用test测试代码，使用显卡时在群里知会一下。

### 第二步：同步主分支

在准备合并代码之前，先将 `main` 的最新内容同步到自己的分支，解决可能出现的代码冲突，并检查代码是否正常运行。

### 第三步：提交合并申请

当个人负责的任务达到阶段性完成标准后，向 `main` 主分支发起 Pull Request（PR），说明本次修改的内容和测试结果。

### 第四步：审核并合并

由组长检查代码，确认修改内容合理、没有明显冲突且通过必要测试后，将 PR 合并到 `main`。并在微信群中告知。

### 第五步：全体成员同步

当 `main` 更新后，所有成员都应将最新的主分支内容同步到自己的工作分支，再继续后续开发。

## 四、分支管理规则

1. **主分支保持稳定：** `main` 用于存放已经整合并经过基本验证的代码，尽量避免直接在该分支上开发。
2. **职责分离：** 每位成员原则上只在自己负责的分支上进行日常开发。
3. **定期提交：** 完成一个有意义的小功能或修复后，及时提交代码，并使用清晰的提交说明。
4. **通过 PR 合并：** 个人分支的代码通过 Pull Request 合并到 `main`，便于审核、讨论和追踪修改记录。
5. **及时同步：** 合并或拉取主分支更新后，及时同步其他成员需要的最新代码，减少分支之间的差异。
6. **谨慎处理冲突：** 如果多人修改了相同文件或代码区域，应先沟通，再解决冲突，避免覆盖其他成员的有效修改。
7. **合并前进行验证：** 对涉及多个模块的修改，合并前应进行必要的测试，确保各模块能够正常协作。

## 五、Commit 提交说明规范

建议使用简洁、明确的提交说明，便于查看项目历史记录。

| 前缀     | 含义     | 示例                      |
| `feat:`  | 新增功能 | `feat: 实现 ARM 感知功能` |
| `fix:`   | 修复问题 | `fix: 修复运动规划逻辑`   |
| `test:`  | 测试相关 | `test: 验证篮子放置功能`  |
| `docs:`  | 文档更新 | `docs: 更新项目说明`      |
| `refactor:` | 代码重构 | `refactor: 优化感知模块结构` |
